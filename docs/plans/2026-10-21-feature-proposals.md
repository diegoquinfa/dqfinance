# Feature proposals

Vision: a decentralized, agent-first (MCP) system for personal **and group** finance. Each person keeps their
financial data on their own deployment instead of someone else's cloud, and instances talk to each other.

Ideas to evaluate, not committed work. When one is picked up it gets a plan in `odd/tasks/`. Related user
feedback is in [2026-10-20-user-feedback.md](2026-10-20-user-feedback.md).

## 1. Safe to spend today

The number the user checks most: how much can I spend **today**, not how much have I spent. One daily figure
that already accounts for:

- fixed and recurring expenses still due before the next income,
- money set aside for savings goals and annual bills (proposals 4 and 5),
- what is left until the next expected income (proposal 7, so not only a monthly salary).

Decided: divide by the days **left**, not the days of the month, so the number corrects itself (overspend
yesterday and today drops; underspend and it rises).

```
today = (available − pending fixed expenses − this month's savings and set-asides) / days left
```

The user also sets a **monthly spending target**. It works as a cap: if the formula gives more than what is left
of that target divided by the days left, the lower value wins. "Days left" runs to the end of the month or to the
next expected income (proposal 7).

## 2. Forecast

Projected balance at the end of the month, and optionally 3 months out, from the current spending pace plus
known recurring expenses and expected income. Shares its calculation with proposal 1 and covers the month-end
projection Kriz911 asked for.

Decided: **separate from proposal 1**. Forecast answers "where am I heading if nothing changes": the balance
left at month end if the current average daily spending continues, minus the fixed expenses still due, plus
expected income. Proposal 1 answers "how much may I spend today to arrive well". They can share helpers in the
backend but are different features and views (forecast as a line chart to month end, warning if it nears zero).

## 3. Reminders of upcoming expenses

Recurring expenses, the "to confirm" inbox and Web Push already exist. Missing: warn **before** the due date
("tomorrow Netflix charges 45,000 COP"), with a configurable lead time per user.

### Outgoing webhooks

Besides push, each user can configure an HTTPS endpoint (for example a Grok Bot routine) that receives the
reminder:

- **Storage:** endpoint URL and optional auth header per user in D1, encrypted with AES-GCM under a master key
  kept as a Worker secret (`WEBHOOK_ENC_KEY`). The panel never shows the secret again, only its last 4
  characters; it can be replaced or deleted.
- **URL validation:** `https://` only; reject `localhost`, private and literal IPs, and non-standard ports.
- **Signature:** a per-user signing secret generated by dqfinance; each request carries an HMAC-SHA256 of
  timestamp + body (`X-DQF-Signature`, `X-DQF-Timestamp`) so receivers can verify origin and reject replays.
- **Test button:** sends a sample event and shows the HTTP status.
- **Delivery:** a daily Cron Trigger finds recurring expenses with `next_due_on` = tomorrow (user timezone) and
  enqueues them in Cloudflare Queues, with retries and backoff. Keep a delivery log per user (time, status,
  code) and disable the webhook after N consecutive failures.
- **Minimal payload:** name, amount, currency, due date, source. Never balances or account details.

```json
{ "type": "payment.due", "dueOn": "2026-10-22", "items": [
  { "name": "Netflix", "amount": "45000", "currency": "COP", "source": "Visa ••4242" } ] }
```

## 4. Annual bills spread across the year

Yearly bills (insurance, property tax, vehicle inspection) should not arrive as a surprise. A yearly recurring
expense sets aside `amount / 12` each month in the budget and in proposal 1, so the money is there when the
bill comes.

## 5. Spread an unexpected expense over several months

When something breaks (the washing machine), the user can spread that expense over N months for budgeting
purposes so the current month does not drop to zero. The transaction keeps its real date and amount; only the
budget and safe-to-spend views see it in installments.

## 6. Savings goals

A goal with amount and date ("trip, 3M COP by June"), contributions and progress. Feeds proposal 1. Already on
the Later list.

## 7. Irregular income

Not everyone has one monthly salary: freelancers, weekly pay, several small incomes. Allow several expected
incomes with their own frequency (weekly, biweekly, monthly, irregular) or an estimate from recent history, and
use them in proposals 1 and 2 instead of assuming a payday.

## 8. Shared expenses

Split an expense with other people and track who owes whom. Overlaps with loans and debts on the Later list.

Decided: built on top of proposal 10 (federated contacts). A contact who is not on dqfinance stays a plain
Counterparty and the split is only recorded locally (Splitwise style). A connected dqfinance contact receives the
split as a request to accept or reject, and on accept it lands in their own books.

## 9. Custom categories

Today categories can only be created. Add edit, delete or merge (moving their transactions), icon and color,
and maybe subcategories.

## 10. Federated contacts (Mastodon style)

Signed-in users connect with each other, whether they share an instance or each one runs an independent
deployment. This is the base for shared expenses (proposal 8) and for sending money between people.

- **Identity:** each user has a handle `user@instance` (for example `diego@finance.diegoquinfa.dev`). The
  instance publishes discovery with WebFinger (`/.well-known/webfinger`) and a per-user Ed25519 public key.
- **Same origin vs. remote:** the contact record stores whether the other user is on the same instance (local
  delivery, no network call) or on another one (its origin and public key).
- **Connecting:** A sends a contact request, B accepts or rejects. Nothing is exchanged before acceptance, and
  either side can remove or block the contact.
- **Server to server:** requests between instances are signed (HTTP Message Signatures with the user's key), with
  a timestamp and nonce against replays. The receiving instance verifies the signature against the key it
  fetched for that handle. Only HTTPS origins; same SSRF rules as the webhooks in proposal 3.
- **Money and splits are requests:** when A records "sent 50,000 COP to B" or splits an expense with B, B gets a
  notification (Web Push and inbox) to **accept or reject**. Accept creates the matching movement in B's books
  (income, or a debt for a split). Reject leaves a note on A's side. Nothing is written in B's books without
  B's action.
- **Minimal data:** only the amount, currency, date, a short title and the handles travel. Never balances,
  accounts or categories.
- **Simple first:** start with contacts and money requests between instances. Groups, multi-person splits and a
  shared ledger come later.

- **Events and broker:** instances exchange domain events (`money.sent`, `split.requested`,
  `request.accepted`, ...) through a queue (Cloudflare Queues) instead of direct calls, so a peer that is down
  receives them later. Events need ids for idempotency, retries with backoff, a dead-letter queue, and a way to
  reconcile state when two instances disagree.
- **Split calculator:** split an expense among friends (equal, by amount or by percentage); each share becomes a
  **pending transaction** in the other person's instance until they accept it.

Open questions: whether to use ActivityPub itself (interoperable but heavy) or a small dqfinance protocol with
the same ideas; how an instance handles an unreachable peer (a queue with retries); and whether open sign-up
instances need rate limits on contact requests.


## 11. Expense search (keyword + semantic)

Find movements by what they were, both from the web and from an agent over MCP. Today there is no search over
transactions.

- **Indexed fields:** title, description and category name only. Never amounts, accounts or balances
  (approved by the user).
- **Keyword search:** exact words and phrases with D1 FTS5 (an external-content virtual table kept in sync by
  triggers on `transaction` and category renames). Accent and case insensitive (`unicode61 remove_diacritics`).
- **Semantic search:** natural-language queries such as "búscame los gastos que hice en Web Sunday". Embed
  title + description + category with Workers AI (a multilingual model such as `@cf/baai/bge-m3`) and store the
  vectors in Vectorize with `userId` as metadata, filtered on every query. Embed on create and update, delete on
  delete, and backfill existing rows with a one-off job.
- **Hybrid ranking:** run both and merge with reciprocal rank fusion, so an exact match always ranks first and
  semantic hits fill in. Optional filters: date range, type, category.
- **Compact for agents:** one MCP tool, `search_transactions { query, from?, to?, limit? }` (default limit 10,
  max 50). Each hit is one short line, for example
  `t_123 · 2026-10-12 · Web Sunday ticket · Eventos · -120.000 COP`, plus a total count and a cursor. No
  descriptions or nested objects; the agent asks for one movement's details only when it needs them. The amount
  appears in the result but is not indexed.
- **Privacy:** the query and indexed text go to Workers AI inside the same Cloudflare account; nothing leaves to
  third parties.

Open question: keep semantic search behind a per-instance flag, since self-hosted deployments must enable Workers
AI and Vectorize.

## 12. Group projects (shared budget)

A shared space where several people pool money and expenses toward one goal, for example a trip to Canada:
someone puts in X, someone else spends Y, and everyone sees where the budget stands. Builds on proposal 10.

- **Shared budget:** a target amount and date; members record contributions and expenses against it, and the
  project shows total, remaining and who owes whom.
- **Custodian (optional):** one member is designated to receive and hold the pooled money, so contributions are
  transfers to that person and group expenses come out of their account.
- **Individual goals inside the group:** instead of pooling, each member tracks a personal savings goal toward
  the shared plan ("Juan reached his 500,000 COP and bought the plane tickets"), and the group sees everyone's
  progress. Unlike a bank pocket, the progress state is shared across people.
- **Sync across instances:** members may be on the same instance or on different deployments; the project state
  is replicated with the events from proposal 10, and failures are handled by the queue.

Open questions: who owns the project's canonical state when members are on different instances (the creator's
instance, or a replicated log every member keeps); and how a member leaves with a balance still open.
